## Understanding Device Triggers

This integration implements a handful of device triggers to make some automation scenarios a little easier to achieve by point and click and without requiring a deeper understanding of the various sensors the printer exposes or where the information is not exposed from sensors such as transient print error notifications from the printer

Every event includes the printer's `device_id` and `name`, and a `type` with the unlocalized name of the event. Some events add more data, listed below.

Available events:

| Trigger | When it fires | Extra data |
|---|---|---|
| Print started | A print starts. | |
| Print finished | A print finishes. | |
| Print canceled | A print is canceled. | |
| Print failed | A print fails. This works on every model, not only the X1. A canceled print fires *Print canceled* instead. | |
| Print layer changed | The print moves to a new layer. The printer's updates lag by a second or two, and if several layers pass between two updates it fires once. | `layer`, `total_layers` |
| HMS error | The printer reports an HMS error. If there are several, you get the most recent one. | `code`, `error`, `url` (wiki link for the error) |
| HMS error cleared | The printer has no HMS errors any more. | |
| Print error | The printer reports a print error. This is a separate set of errors that aren't surfaced as HMS errors. No I don't know why. | `code`, `error` |
| Print error cleared | The print error goes away. | |
| Missing SD card | The printer reports that its SD card is missing. It fires once, and again only after a card has been seen in between. | |
| Timelapse downloaded | The integration has saved a print's timelapse to Home Assistant. This needs the timelapse cache to be enabled in the printer's options. | `path`, `url` |

For the most part these are just conveniences - you could craft an automation triggering the same way but it takes a bit more effort to understand which sensor(s) to use to track the activity you want which requires understanding how the sensors and what the available states are.

The print canceled and print error events are only a transient event from the printer rather than a persistent state so these are not available from sensors.

The printer sensor that exposes HMS errors as a list would be very complex to handle correctly in the multi-error case, so the HMS error event just gives you the most recent error to allow much easier handling in a notification.

The X1 reports its routine first layer inspection (HMS_0C00_0300_0003_000B) as an HMS error while it runs. It isn't a problem, so it is left out of the HMS errors sensor and events. Anything the inspection finds is still reported.

<Info>
  For *Timelapse downloaded*, `path` is where the video was saved. `url` is only filled in when that file is under Home Assistant's `www` folder. The print cache is kept out of `www` because Home Assistant serves that folder without authentication, so `url` is normally empty. Use `path` instead.
</Info>

When crafting a notification or similar you can access the event data with a template of `{{ trigger.event.data.[data_name] }}` - e.g. `{{ trigger.event.data.error }}`.

## Actions for Device Triggers

These can be whatever you like. The most interesting case is the *HMS error* trigger. This has six pieces of data payload in it:
- device_id
- name
- type (unlocalized name for the event)
- code
- error
- url

These can be accessed using the Jinja2 templating syntax in the action. So for example if you wanted to trigger a notification you would be able to set the title text to

```
Printer Error on {{ trigger.event.data.name }}
```

and the message text to

```
{{ trigger.event.data.code }}: {{ trigger.event.data.error }}
```

Note that doing this will kick you out of the visual editor and into editing the raw yaml.
